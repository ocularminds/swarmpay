**Run your own SwarmPay on Render**

[`render.yaml`](../render.yaml) deploys a complete SwarmPay to [Render](https://render.com) from this repository: the web front end, the commerce application and its agents, the private payment executor, the AgentSafe gateway, the simulated venue, the egress proxy and PostgreSQL. Payments are **simulated**, AgentSafe decides them with its **local test authority**, and agents are simulated unless you add a model. It is a copy anyone can deploy to try the whole journey; the hosted demo at swarm.decionis.com stays the PayPal sandbox deployment.

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/ocularminds/swarmpay)

**What it costs.** Render's free tier covers the public web front end only; private services start at the Starter instance type, so the other six services each run on Starter, with a 1 GB disk for PostgreSQL and one for AgentSafe's evidence journal. Check [Render's pricing](https://render.com/pricing) before deploying, and suspend or delete the services when you're done.

**What Render can't enforce.** On AKS and in Compose, network policies keep the agents' service away from everything but its proxy, PostgreSQL and the gateway, and away from PayPal entirely. Render's private network doesn't offer those rules. This copy therefore never holds PayPal credentials, the application still sends its outbound HTTPS through the egress proxy (which refuses PayPal by name), and the separation of database roles, the gateway and the executor's checks are unchanged. Treat it as a demonstration, not a place for real accounts.

**Deploy**

1. Generate the simulated venue's keypair: `node demo/render-keys.mjs`. It writes both values, owner-only, to `.local/render/venue-keys.env`.
2. Choose **Deploy to Render** above, or **New → Blueprint** in Render with this repository. Render asks for the values the Blueprint doesn't generate:
   - `SWARM_PUBLIC_ORIGIN` on `swarm-pay-commerce`: the public URL of `swarm-pay-web`, normally `https://swarm-pay-web.onrender.com`. If Render gives the web service a different URL, update this value and restart `swarm-pay-commerce`.
   - `ORGANIZER_PASSWORD` on `swarm-pay-commerce`: the password you will sign in with, as `organizer`.
   - `VENUE_PUBLIC_KEY` on `swarm-pay-executor` and `VENUE_PRIVATE_KEY` on `swarm-pay-venue`: the two lines from step 1. Then delete the file.
3. When the services are live, open the web URL, describe an event, and sign in as `organizer` with your password. Everything else follows the [walkthrough](../demo/walkthrough.md).

Database passwords, the executor token and the MCP token are generated by Render and shared between services through the Blueprint; none is written in the repository. Optional: `CHANNEL3_API_KEY` on `swarm-pay-commerce` adds tents to buy ([sandbox setup](sandbox-setup.md)).

**How the services find each other.** Render's private hostnames carry a suffix (`swarm-pay-commerce-ab12`), so each service gets its peers' `host:port` from the Blueprint (`DATABASE_HOSTPORT`, `AGENTSAFE_HOSTPORT`, `EGRESS_HOSTPORT`, `COMMERCE_HOSTPORT`, `AGENTSAFE_UPSTREAM_HOSTPORT` and the web's `SWARM_*_UPSTREAM`), and the web front end reads its DNS server from the container (`SWARM_NGINX_RESOLVER=auto`). `node demo/render/check.mjs` runs the local stack wired exactly that way and passes the smoke test before restoring the ordinary wiring; CI runs it on every change. `render.yaml` is generated from [`infra/render/blueprint.mjs`](../infra/render/blueprint.mjs), and its test checks that every reference resolves and no secret is written inline.
